# 作业01 —— 需求与方案分析（高弨 · 组员/开发）

**课程：**《软件工程行业案例分析与实现》· 人工智能Ⅱ方向　**姓名：** 高弨　**角色：** 组员（开发，负责核心功能）

## 1. 角色与目标
本人在小组中负责**核心功能的开发**（约占项目核心功能的一半）：两个感知模块——**语音分析**与**文本理解与评价**的全链路实现，以及**融合评分引擎与可追溯报告**。目标：让两个感知模块处理新输入并返回真实结果，且评测报告能追溯输入数据与评分规则。

## 2. 项目主要业务流程（本人负责部分加粗）
1. 候选人完成作答（文字/语音）→ 2. **评分任务异步触发** → 3. **文本理解与评价：DeepSeek 语义评分（分档规则）** → 4. **语音分析：Java 聚合录音段 → Python 服务分析 → 四维子分** → 5. **证据落库（voice_evidence / text_evidence）** → 6. **融合评分与报告生成** → 7. 报告页逐题展示。

## 3. 核心数据对象（≥2 个）
- **Evaluation（逐题评测）**：新增 `voice_score`/`voice_evidence` 与 `text_evidence` 字段（Flyway V48/V49）。`text_evidence` 结构化记录：模块标识、评分规则版本、输入文本摘要与长度、命中分档及定义、四维原始分与校准分；
- **interview_recording_segment（录音段）**：语音分析按 `interview_question_id` 聚合该题全部录音段（多段按时长加权融合），解决了"音频未回写回答记录"的链路断点；
- **MediaFile / 本地对象存储**：录音文件落盘，backend 与 voice-analysis 共享 `media_data` 卷，路径一致才能读到文件。

## 4. 所选 AI 功能与验收标准（本人负责）
| 功能 | 验收标准 |
| --- | --- |
| 语音分析 | 新录音输入 → ffmpeg 转码 → librosa 分析 → 四维子分真实返回并落库；现场可复现 |
| 文本理解与评价 | 新文本输入 → DeepSeek 按分档规则评分 → text_evidence 落库（输入摘要/分档/规则版本）；现场可复现 |
| 融合评分与报告 | 两个感知结果进入评分规则；报告接口返回 questionVoiceReviews / questionTextReviews；未测维度显示"未评估" |

## 5. 架构方案与理由
- **语音分析独立轻量 Python 服务**：librosa/soundfile/ffmpeg 生态在 Python 最成熟；FastAPI 暴露 `POST /v1/analyze`，与 Java 通过内网 HTTP 解耦，共享卷避免文件二次传输；
- **文本理解复用语义评分引擎**：不重复造轮子，在其上补"可追溯证据层"——评分时同步生成结构化 evidence JSON，最小改动满足验收；
- **旁路增强设计**：语音分析失败只降级为"未评估"，不阻断文本评分主链路，保证验收演示稳定性；
- **健壮性措施**：webm 格式 ffmpeg 兜底转码、pyin 限长（前 30 秒）、readTimeout 提升至 60s、多段录音按时长加权——均来自真实联调中发现并修复的问题。
